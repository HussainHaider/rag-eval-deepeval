# rag-eval

A small RAG system built over the **"LLM Evals" YouTube session transcripts**, together with the
golden datasets used to evaluate it with [DeepEval](https://github.com/confident-ai/deepeval).

The retrieval side is LangChain + Chroma + OpenAI embeddings. The evaluation side is a set of
hand-written and synthesized golden datasets covering retrieval quality, answer correctness,
faithfulness, scope control, prompt/data leakage, and toxicity.

## What's in here

| Path | What it is |
| --- | --- |
| `data/*.vtt` | Source material: 8 WebVTT transcripts of the LLM Evals sessions. |
| `src/retriever.py` | Loads + cleans the VTTs, chunks them, embeds them into a persisted Chroma store, and exposes a retriever. |
| `goldens/` | The evaluation datasets (JSON) plus `generate_goldens.py`, which synthesizes draft goldens from the transcripts. |
| `evals/` | Where the DeepEval test suites live (currently empty — this is the next piece of work). |
| `resources/deepeval_intro.py` | A minimal standalone DeepEval example: two test cases scored with `AnswerRelevancyMetric`. |
| `export_chroma_chunks.py` | Dumps every chunk in the Chroma store to `chunks_dump.json` so you can scan them by hand. |
| `main.py` | Placeholder entry point. |

### The golden datasets

Each file holds 15 cases. They use different schemas because they test different things:

- **`retriever_goldens.json`** — `query` / `ideal_answer`. Hand-written retrieval questions.
- **`retriever_deepeval_goldens.json`** — same schema, but machine-generated by `generate_goldens.py`.
  Its `source` fields are still `"TODO-verify"`; review these before trusting them.
- **`correctness_goldens.json`** — `question` / `ideal_answer`. End-to-end answer quality.
- **`faithfulness_dataset.json`** — `query` / `ideal_context`. The chunks an answer must be grounded in.
- **`scope_goldens.json`** — `input` / `expected_action` (`ANSWER` or refuse) plus `success_criteria`.
  Checks the app stays on-topic.
- **`leakage_goldens.json`** — adversarial prompts trying to extract the system prompt; `expected_action` is `DECLINE`.
- **`toxicity_goldens.json`** — prompts designed to provoke abusive output.

## Requirements

- Python **3.11+**
- [`uv`](https://docs.astral.sh/uv/) for dependency management
- An OpenAI API key (used for embeddings, generation, and as the DeepEval judge model)

## Setup

```bash
# 1. clone and enter the project
git clone https://github.com/HussainHaider/rag-eval-deepeval.git
cd rag-eval-deepeval

# 2. install dependencies into a local .venv
uv sync

# 3. add your API key
echo 'OPENAI_API_KEY=sk-...' > .env
```

`.env` is gitignored and is loaded automatically by `python-dotenv` in every script — you don't
need to export anything or activate the venv manually if you run things through `uv run`.

## Build the vector store

The store is built lazily. The first run reads `data/*.vtt`, strips the WebVTT timestamps, splits
each transcript into 1000-character chunks with 150 characters of overlap, embeds them with
`text-embedding-3-large`, and persists the result to `chroma_store/`. Every run after that just
opens the existing directory, so you only pay for embeddings once.

To build it and smoke-test retrieval in one step:

```bash
uv run python src/retriever.py
```

That runs the sample query in `__main__` ("what is regression testing?") and prints the top 5
chunks with their session numbers. If you see results, the store is built and working.

> To rebuild from scratch — after editing `data/` or changing the chunking — delete the store first:
> `rm -rf chroma_store` and re-run the command above. Note that `chroma_store/` is **not** in
> `.gitignore`; add it before committing if you don't want the embeddings in the repo.

## Run things

```bash
# inspect every stored chunk -> chunks_dump.json, plus a per-session count
uv run python export_chroma_chunks.py

# the standalone DeepEval example (2 cases, AnswerRelevancyMetric)
uv run python resources/deepeval_intro.py

# regenerate the synthetic goldens (OVERWRITES goldens/retriever_deepeval_goldens.json)
uv run python goldens/generate_goldens.py

# placeholder entry point
uv run python main.py
```

Eval suites go in `evals/` and are run with `pytest` (already a dependency):

```bash
uv run pytest evals/
```

`evals/` is empty right now, so that command collects nothing and pytest exits with code 5
("no tests ran") until you add test files.

## Using the retriever in your own code

```python
from src.retriever import build_retriever

retriever = build_retriever()                 # k=5 by default
docs = retriever.invoke("what is an LLM judge?")

for d in docs:
    print(d.metadata["session"], d.page_content[:200])
```

`load_store()` is the lower-level alternative — it returns the `Chroma` object itself, which is
what you want when you need raw collection access (see `export_chroma_chunks.py`).

## Configuration

Models and chunking are pinned in code rather than in config, so change them where they live:

| Setting | Value | Where |
| --- | --- | --- |
| Embedding model | `text-embedding-3-large` | `src/retriever.py` |
| Chunk size / overlap | 1000 / 150 | `src/retriever.py`, `goldens/generate_goldens.py` |
| Retrieved documents (`k`) | 5 | `src/retriever.py` |
| Golden synthesizer model | `gpt-4.1-mini` | `goldens/generate_goldens.py` |
| Judge model | `gpt-4.1` | `resources/deepeval_intro.py` |

If you change the embedding model or the chunking, delete `chroma_store/` and rebuild — the
existing embeddings will no longer match.

## Costs and gotchas

- Building the store embeds all 8 transcripts in one pass. It's cheap, but it is a real API call.
- DeepEval metrics are LLM-judged, so every eval run costs tokens. Keep golden sets small (15 is
  deliberate) and pin the judge model so scores stay comparable between runs.
- `generate_goldens.py` samples chunks at random and writes draft goldens. **Review every one**
  before using them — check grounding, trim padding, and fix leading questions.
